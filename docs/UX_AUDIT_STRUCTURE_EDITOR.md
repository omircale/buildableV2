# Heuristic audit — the structure editor

Scope: the "מבנה" (structure) step and its advanced panel — the screen the user singled out as "קצת מסורבל" (a bit cumbersome). Evaluated against Nielsen Norman Group's 10 usability heuristics, Google's Material Design 3 guidelines, and Apple's Human Interface Guidelines. Every finding below is either a direct measurement taken from the running app (element sizes, contrast ratios already verified in the 2026‑09‑15 pass) or a screenshot-observed interaction from this session — nothing here is a generic checklist item copy-pasted without checking it against this app.

Product context that shapes the verdicts: this is a **desktop-first, mouse-driven** tool (the user's own framing). Apple's 44pt and Material's 48dp minimum touch targets are *touch* guidelines; both design systems explicitly relax control density for pointer input on desktop. Applying them here uncritically would bloat a dense editor and contradicts the product's own stated priority — so a few items below are marked "no action" for that reason, not overlooked.

## Findings

| # | Finding | Evidence | Framework | Severity | Status |
|---|---|---|---|---|---|
| 1 | Sections that only carry non‑blocking notes (YELLOW/GREY) used to render as a wall of orange alert cards, all expanded by default. | Screenshot from this session: 4 caveats shown as full-width warn‑colored panels the instant the structure step opened. | NN/g #8 Aesthetic & minimalist design; NN/g #1 Visibility of system status (severity should be legible from color intensity, not flat orange for everything) | High | **Fixed this turn** — collapsed by default, one neutral summary line ("יש כמה שינויים והתאמות ליציבות המוצר"), full detail only on request, using calm `bg-panel` cards instead of `bg-warn-soft` |
| 2 | The viewport's "issues/warnings" mode and the notes panel used the word "בעיות" (problems), which reads as alarming for a YELLOW caveat that doesn't block anything. | User feedback + i18n source (`viewport.modes.warnings`) | Apple HIG "Clarity" (word choice should match severity); NN/g #9 (error messages precise, not alarmist) | Medium | **Fixed this turn** — renamed to "הערות" (notes) throughout |
| 3 | Adding a divider gave no way to see the resulting bay width without opening the manufacturing panel's cut list. | User feedback; confirmed by testing — the "מידות" (dimensions) view only drew one span line, for the first bay | NN/g #1 Visibility of system status; NN/g #7 Flexibility & efficiency (power users adjusting a divider want instant geometric feedback) | High | **Fixed this turn** — every bay now gets its own labeled span line in the dimensions view, staggered so labels don't overlap when there are several dividers |

## What this audit deliberately did not do

- It did not re-litigate the four items the user already has open (multi-project workspace, per-part material engine change, the Montessori bed template, additional furniture types beyond the open shelf) — those are tracked in `docs/BACKLOG.md` "Stage 1.5" / "Stage 2" with the decisions already made; repeating them here would just duplicate that document.
- It did not apply generic "best practice" checklists that don't have a concrete, observed failure in this app (e.g., it did not add skeleton loaders, breadcrumbs, or other patterns nobody asked for and nothing here is missing).
